## Priorities

1. The user's instructions
2. Consistency with the codebase
3. This file

## Keep the docs in step

Docs are part of the change, not a follow-up. At the end of every task, before
calling it done, check them against what you changed and update them in the
same branch:

- **`docs/src/`**, the handbook. Find the chapter that describes what you
  touched (`docs/src/SUMMARY.md` lists them) and make it true again. A new
  plugin, setting, browser, command or file belongs somewhere in it. A new
  topic gets its own page, added to `SUMMARY.md` and to the README's chapter
  table.
- **`README.md`**, the short version: features, quick start, chapter table.
- **`CHANGELOG.md`**, under `[Unreleased]`, for anything a user would notice.
  CI and repo plumbing don't need an entry.
- **`IDEAS.md`**: when you build something it lists, say so there or remove it.

If nothing needed changing, say so in your summary rather than skipping the
check. State only what the code does: verify a claim against the code, or
against the browser, before writing it. When you can't verify something (a
browser you can't run, say), write that it's unconfirmed.

## Write down the non-obvious

Every time you hit something that surprised you, or that the next person would
get wrong, write it down before moving on:

- A gotcha about the code, a browser, caelestia or the tooling goes in
  `docs/src/architecture/hazards.md`, dated, with what goes wrong and what to
  do instead.
- A rule about how to work in this repo goes in this file.
- A why that only makes sense next to the code goes in a comment there.

Examples of the bar: an API that silently ignores something, a limit that
fails with a misleading error, an approach that looks right and isn't. If you
lost more than a few minutes to it, it qualifies.

## Architecture in one breath

A Rust native messaging helper (`src/`) reads caelestia's files and streams
them to the extension. The extension (`extension/`, Svelte 5 and TypeScript,
built by Vite into `extension/dist/`) keeps everything in `storage.local`,
which the new tab and the content scripts watch. Widgets are `Ct*` components
in `extension/src/components/widgets/`, styled with Tailwind classes only (no
`<style>` blocks; a run-time value goes in as a CSS variable read by a class,
like `opacity-(--dim)`); anything that needs
the machine is a data plugin in `src/plugins/`. The details are in
`docs/src/architecture/`.

Two constraints shape everything. Design with them; there is no way around them:

- The extension can't run code it didn't ship (Manifest V3, and both stores
  reject remote code). User or plugin logic that isn't bundled runs in the
  helper; the page gets data and CSS.
- The background page can be suspended at any time. State that must survive
  lives in `storage.local` or in the content script, never only in the
  background's memory.

## Core rules

### KISS

Write straightforward code. No indirection for its own sake, no abstractions
that exist only to satisfy a module boundary.

### YAGNI

- No features beyond what was asked for.
- No abstractions for single-use code; extract at three uses, not two.
- No configurability nobody asked for.
- No error handling for things that can't happen.

### Surgical changes

Touch only what the task needs. Match the existing style. Mention unrelated
dead code rather than deleting it.

### Comments

Write like a contributor. A comment explains what the code can't say for
itself: a why, a gotcha, a ceiling. A deliberate shortcut with a known limit
gets a `ponytail:` comment naming the limit and the way out.

## Vendored code

`extension/public/userstyles/` and `extension/public/vendor/` are generated by
`scripts/vendor-userstyles.mjs` and `scripts/vendor-nerd-fonts.sh`. Never edit
them by hand; change the script or the pinned version and run it again.

## Verification gates

Match CI locally before pushing:

- `cargo fmt --check`
- `cargo clippy --all-targets -- -D warnings`
- `cargo test`
- `node --test tests/*.test.mjs`
- `npm run --prefix extension check` and `npm run --prefix extension build`
- `web-ext lint --source-dir extension/dist --self-hosted` (warnings are
  expected from less.js and Svelte's runtime; errors aren't)
- `mdbook build docs` when the docs changed

For anything that touches the helper, storage or injection, run
`tests/e2e-firefox.mjs` (see the Development chapter); for anything a user
does on the new tab, the Playwright tests (`npm run --prefix extension test`),
and add a test for a new interaction. Use Playwright's locators by role and
label, which is also why every field's label names its control and nothing
else. The pre-push hook runs
it; CI can't, so a push that skips the hook skips the test. For anything visible on
the new tab, look at it: `web-ext run`, or a screenshot through the e2e test's
WebDriver session.
